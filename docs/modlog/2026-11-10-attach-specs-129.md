## Effect attachments: the linked target, op 0x7b's offset, the spin ops checked (2026-11-10)

Modlog-gaps item 129 ("Effect motions from specs: op 0x7b's two-point offsets, 0x33 and modes 7 / 8 at start, the spin
ops' attachment rebuild"). The row was written before "Effect stream ops: ground snap, point offsets, emitter spin,
no-ops" built all three; this entry checks that build against Steven's FFXiMain.dll (disassembly) and fixes what
differed.

- Op 0x7b's offsets, as built: FUN_10053e60 (0x10053e8b..0x10053f0e) and op 0x11's FUN_10053c80 pass A = op +4..+0xc
  and B = op +0x10..+0x18 to FUN_1003be10 when gen +0x98 is set. A always goes with the caster point pc and B with
  the target point pt: modes 3 / 0x16, 6 / 0x19, 0xd / 0x1a, 0x12 / 0x1b, and 0x10 / 0x11 (both points on one
  actor); every other mode passes 0. FUN_1003b980's fourth argument (0, or 1 from 0xd / 0x1a) is never read: the
  frame is Euler(0, -atan2(dz, dx), atan2(dy, |dxz|)) at the first point and the distance in every mode.
- Fixed: the offset's turn. FUN_1003ba20 turns it with RotationY(vtable +0x1c0's y) and TransformCoord (math vtable
  +0x64 / +0x50): the actor's yaw alone. Ours turned it by the whole actor frame, so a ground-tilted actor's offset
  leaned with it.
- Fixed: point 0x30 with an offset. Case 0x30 takes vtable +0x1c4(0) as it is, runs the segment from 1 above to 6
  below (FUN_10181590) and never adds the offset. Ours started the segment at the offset point. 15 generators carry
  an offset on point 0x30: mode 3 with pc and pt 0x30 in 49430, 50180 and 87164 (`gp03 gp04 ur01 bp01 my01`, A
  (0, -5.9 / -6.9, 0), B (0, -2.5, 0)): both ends are the ground under the two actors in retail. The cases 0x31 /
  0x32 / 0x33 add the offset to each candidate 0xd..0x14 before the distance test (0x1003bc2c..), 0x34 / 0x35 take
  none, as ours.
- Fixed: modes 0x16..0x1b. FUN_1003be10 (0x1003be73..0x1003be84) asks FUN_100845e0(caster) -> FUN_10098360: the
  entity of index entity +0x1f8 (table DAT_10480af0), when it has +0x120 bit 9, gives its actor +0xa0, and that
  actor stands in for the target in these six modes; with none the target stays. +0x1f8 is the face target of the
  0x00D / 0x00E updates ((u32 @0x18 >> 17) & 0x7fff, writers 0x1009a0b1 / 0x1009bc50), the one the head look uses.
  Ours used the task's target. Actors::face_target (the client: Entity::face; we are not in the entity table, so our
  own casts keep the target). Only mode 0x1a is in the data: 192 generators in 101739..101802.
- Point 0x33 and modes 7 / 8 at the start, as built: attach_now takes the last frame's eye and camera. 0x33 reads
  FUN_10015250() +0x44 (the camera position), modes 7 / 8 copy DAT_1047bfa8 +0xc10 whole and set row 3 to the point
  (no offset). 23 generators in 14 files use point 0x33; modes 7 / 8 have 4 and 1 generators.
- The spin ops, as built: update jump table 0x1004a814 entries 0x0e / 0x0f / 0x10 = 0x1004a0b6 / 0x1004a236 /
  0x1004a3b6. Each calls FUN_10053e60 (the attachment again, into the generator's own matrix), builds the turn in
  the walker's pool matrix (math vtable +0x60 X, +0x64 Y, +0x68 Z), sets row 3 aside, multiplies out = out x R
  (vtable +0x24) and puts row 3 back. 4,134 generators in 353 files have one, all in modes 1 / 2.
- Census (dat::generator::tests::attach_spec_census, 34 s): 152 generators read op 0x7b's offsets in a two-point
  mode, 17 set them in a mode that never reads them.
- Not done: the linked target's CPU pose (Effects::posed_actors lists the task's actors only, so a face target
  other than the task's target gives its rest pose until an effect of its own poses it); a doll caster's link
  (FUN_100845e0 reads the doll's +0x70, not traced); retail's (0, 0, 0) on a point 0x30 miss, kept as ours.
