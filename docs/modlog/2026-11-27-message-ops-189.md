Ours:

- `fx::Actors::record_print` is FUN_1009e090's tests (the client's `combat::PrintView::record` / `message`):
  whether the number starts, with its kind, actors, value and colour, and whether the line prints.
- `Effects::print_record` asks it inside the op and starts the number there (`start_number`: `spawn_task` links it
  before the running task, `run_new` is its first update). A task the number's scheduler makes in that update sends
  the walk back to the printing task, as for any scheduler an op starts (row 172). The line's answer goes to the
  client with the print (`action_prints`), which puts the line in the log after the walk, in the same frame.
- `print_next` is FUN_1018dde0 (op 0x2b and `end_action`, FUN_1018dbf0): the record is marked after its print.
  Op 0x71 passes the op's whole u32.
- The action's end inside the update (a task deleted in the walk, a start that fails in `run_pending`, an op's kill)
  prints on the spot. Outside it (`on_action` with no effect file, the client's kills) the records wait for the next
  update's start (`late_prints`).
- Found in the trace and changed with it:
  - the game state: no number and no line while we zone or load (ours printed). Ours has no state value: 0x60 is
    taken as "not zoning and not loading" (as hudtop.rs does); the position packet's modes 8 / 9 are not modelled;
  - FUN_1009e370: `Entity::group` / `World::my_group` from s2c 0x067 kinds 2 and 3 (ours did not read them);
  - a number no longer needs a line mode that shows (ours started none for a hidden mode);
  - a number needs both models (ours started the scheduler without them);
  - a message that is not in the table prints nothing;
  - the chat filter's relation: a party or alliance member's pet counts as the member, and a claimed monster is
    "ours" in a zone that pools treasure (`World::my_pool_off` is our +0x130 bit 25, from a 0x00D about us);
  - op 0x2b prints whatever the task's motions flag is.
- Not changed: the value and the colour are fixed on the number's generators when they start (ours `Instance::dam`),
  so the task has them before its first update; retail's element reads them later, with the same result.
