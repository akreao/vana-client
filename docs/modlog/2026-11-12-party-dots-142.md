## Party dots on the map: the request, the answer, and a live check (2026-11-12)

<!-- dll-build: 30261102_0 -->

Queue row 142. The gaps row still said "Not built", but party positions were built with the markers and their
retail path was re-read for row 141 (the "Where members come from" part of that entry). This is the rest: the two
packets compared with LSB, the answer's handler read once more in Ghidra and Rizin, and a live run with two
characters in a party. Four small things differed in how the answer is taken and are fixed here.

**c2s 0x0D2 (FUN_100f0800).** 8 bytes: ZoneNo u32 at 4, the map window's zone (+0x100, a short, `movsx`). The same
call stores the answer's handler and the map's asked sub-key (+0x102) in the session object (+0x1c794 function
pointer, +0x1c798 the key). Nothing else in the DLL reads or writes those two fields (searched by displacement), so
they are never cleared: the handler set by the first request of a session stays for good. FUN_101fa680 sends it
once per map (+0xa45) and turns on the busy strip (bit 4, FUN_10222880).

**s2c 0x0A0 (FUN_100f07b0).** UniqueID u32 at 4, zone s16 at 8, x / y / z floats at 0xc / 0x10 / 0x14. With no
handler stored the packet does nothing at all. Otherwise it calls the handler with (zone, the *stored* key, id, x,
y, z).

**The handler (FUN_101f94d0).** Busy bit 4 off (FUN_10222910) first, whatever follows. Then: a map window exists,
the id is not ours (+0x3c440), the packet's zone is our zone (+0x3c400), and the sub-key under the position
(FUN_101827a0, 0 with no floor) equals the stored key. The member is looked up by id in the party list; our party's
when the low two flag bits equal ours. The pixel is FUN_101f8a40(zone, stored key, 0) → FUN_101f8b80: the record of
exactly that zone and sub-key, x × (1 / (2560 / |scale|)) × 512 + 0.5 truncated to 16 bits, y negated. Then
FUN_101fa720 places the name on whatever map window is open.

What ours did differently:

- It used the open map's key, not the key stored at the request. Now `Scan::party_key` holds it (set where 0x0D2 is
  sent).
- It took an answer before any map had asked. Now nothing happens until a request has been sent (not even the busy
  strip clears).
- It dropped the answer on a map of another zone. Retail has no such test: a late answer lands on whatever map is
  open (a mode 5 map of another zone never asks itself, but does not refuse one).
- It converted the position through the shown record. Retail looks the record up by (zone, stored key); when the
  zone has no record for that key (the key-0 record is shown instead) the lookup returns -1 and FUN_101f8bd0 reads
  the scale byte 14 bytes before the table, 0x103832af, which is 0x10 in this build. Ours now does the same
  (`reply_px`).
- With no collision loaded ours let any position pass; retail's key is 0 then.

The answer is now applied with the other map requests (`map::Cmd::Party`), where the map records are.

**LSB.** Both layouts match (src/map/packets/c2s/0x0d2_map_group.h, s2c/0x0a0_map_group.h). LSB refuses the request
during an event and when ZoneNo is not the character's zone; it answers with one 0x0A0 for every party and alliance
member in the same zone and Mog House state, the asker included (the client drops its own id). Nothing to change on
the server.

**Live (test server, Bastok Markets, two accounts).** Opencs invited Partyb (`/pcmd add`), Partyb joined. Markers →
Right asked for positions and stayed on set 1; the next Right showed set 2 with Partyb, picking the row labelled it
and scrolled to it. With Partyb standing next to Opencs the dot came from the actor (FUN_101f93c0); after Partyb
warped 148 yalms away (out of actor range, by the third home point) and the map was reopened, the dot was at the
home point: placed by the 0x0A0 answer. Not checked live: alliance members (set 3), a member on another sub-map.

Ours: client/map.rs (`Cmd::Party`, `reply_px`, `px_of`, `party_pos`), the `AskParty` arm in client/mod.rs,
`Scan::party_key` in client/widescan.rs. Test `map::marker_tests::reply_pixel_and_placing`.
