## Map markers: a parity pass over mapv3 / mapv2 and the .MRK file (2026-11-12)

<!-- dll-build: 30261102_0 -->

Queue row 141. The gaps row still said "Not built", but the markers were built on 2026-10-22 ("Markers (mapv3 /
mapv2, spec 5 / 7)" above). This is the audit of that build against FFXiMain 30261102_0: every function of the map
window between 0x101f9200 and 0x101fdc00 read in Ghidra, the float and key paths in Rizin. Thirteen things differed
and are fixed here; what was marked *(inf)* in the first entry is settled. Addresses are 30261102_0 (the first
entry's are 30261006_0: FUN_101f80b0 is now FUN_101f96c0, and so on through `dll.py map`).

**The window's marker records.** The map window holds 40 records of 0x20 bytes at +0x174 (flags u16, sprite kind u8
at +2, alpha u8 at +5, map pixel s16 x 2 at +6, label offset (16, 1) at +0xa, colour index 2 at +0x10, name pointer
at +0x18) over 40 file-shaped records of 0x16 bytes at +0x6d4 (x, y, name[16], valid, pad). Sets 0 and 1 (slots
0..19) are the .MRK file; sets 2 and 3 (slots 20..39) are party and alliance members and are never saved. Flags:
0x80 the slot holds a marker, 1 it is shown (fades in), 8 no label.

**The file (FUN_101f96c0 load, FUN_101f98c0 save).**

- The name is `M%03d%02d.MRK` with the zone and the sub-key the map was *asked* for (+0x102), which is the sub-key
  under the player even when the zone only has a key-0 record and that one is shown. Ours used the record's key.
- The layout follows the file's size, not its name: 0x1c0 bytes is magic, CRC, data; any other size is read whole
  and must be 0x1c8 bytes (magic at 0, CRC at 8, data at 0x10). The old name `M%03d%02d_%08d.MRK` is only the
  second name tried. Ours tied each layout to its name.
- A marker exists only when its valid byte is exactly 1 (`cmp byte, 1`); ours took any non-zero byte.
- FUN_101f95f0 only repairs a name with no NUL in its 16 bytes (the 16th becomes 0); it never fails the file.

**Removing keeps the name (FUN_101fa3b0).** Remove clears the valid byte and the 0x80 flag and nothing else: the
name and the pixel stay in the record and in the file. mapv3's draw (FUN_101fd4d0) prints the name of a set 0 / 1
row whether or not it holds a marker, so a removed marker's row keeps its name next to the empty icon, and placing
there again keeps it. Ours wiped the slot. The event ops 0xa8 / 0xb9 call FUN_101fa3b0 and then FUN_101fa440 with
an empty string, so they clear the name but keep the pixel.

**mapv2 closes after every choice (FUN_101fda10).** All three options end in `FUN_1015fee0("menu    mapv2")`: View
scrolls and closes, Place starts the cursor and closes, Remove removes and closes, Rename opens the name entry and
closes. Ours kept mapv2 open behind each of them. View on an empty slot is disabled at open (FUN_101fd930:
`FUN_10119ff0(5, 1)`), as map0's Wide Scan is.

**mapv2's place (FUN_101fd930), was inferred.** FUN_101fd340 takes the rect of mapv3's cursor row (child row + 1,
FUN_10119d90) and the window moves to (row x0 + own x0 - own x1, row y0): its right edge on the row's left edge, its
top on the row's top.

**The name entry (FUN_101fd3a0, FUN_101fd450).** The shared text input, 15 characters, starting from the slot's
name. mapv3's handler (FUN_101fd680) passes Enter, Left and Right to the input (`FUN_101c7ef0(1 / 5 / 4)`), and the
input's done callback sends message 0x11. Messages 6 (Escape), 9 and 0x11 all end in `FUN_101fd450(1)`
(0x101fd83d: `jne 0x101fd87b`), which copies the input's text into the slot. So Escape keeps what was typed, the
same as Enter; ours discarded it.

**Placing (FUN_101fa130, FUN_101fa1a0).** The cursor starts at the cursor point (W x 200 / 512, H / 2) in the
cursor box, speed 8, as built. On Enter the marker goes to
`trunc(cursor / zoom + view + 0.5) + trunc(sprite width x 0.5 / zoom + 0.5)` on both axes, the sprite being the
cursor (keytops3 151, the window's sprite list entry 1 at +0x118; the width is its x1 - x0, words +0x22 / +0x20, read
each time, so a sprite pack that resizes it moves the point too): the centre of the cursor sprite, not its top-left
corner as ours had it.

**Markers show only while mapv3 is open.** mapv3's open (FUN_101fd280) hands the window the 40 records (+0x94,
count 0x28 at +0x7a) and its close (FUN_101fd310) takes them away, and the window's update and draw walk only that
list (FUN_101f0670 0x101f0e5d, FUN_101f01a0). So the markers vanish the moment mapv3 closes, with no fade-out, and
keep their alpha: opening mapv3 again shows them at once. Only a set change fades (FUN_101fc380 → FUN_101fc350 /
FUN_101fc310: flag 1 off for all 40, on for the shown set's slots with 0x80). The alphas reset when the map window
closes (FUN_101fbb60 → FUN_101fc350(1)). Ours faded them out after the close.

**The fade (FUN_101f0560).** dt x 0.5 x 12 a tick up or down (6 a tick, as built). Two blink flags: 4 turns into
0x400 at 0x80 and falls at 12 x 0.5 (the player arrow, as built); 0x1000 turns into 0x2000 and falls at 3 x 0.5
(`sbb eax, eax; and al, 0xf7; add eax, 0xc`), so an unregistered teleport point drops four times slower than it
rises. Ours blinked those at 6 both ways.

**Sets 2 and 3 (FUN_101fa720).** Fixed slots, not a packed list:

- A member of our party ((flags ^ ours) & 3 == 0) takes the first free slot from 20.
- Any other alliance member takes the first free slot from 0x13 + the party window's count for our party
  (DAT_10665548 + 0x13, which counts us), or from 25 when that window does not exist. A slot of 40 or more is
  dropped.
- A slot already holding the same name ends the search: the first position wins. So an s2c 0x0A0 answer does not
  move a member the actors already placed; ours replaced the position.
- Slots 20..29 are set 2 and 30..39 set 3. Set 3 can be shown only when an alliance member landed in it (+0xa48);
  set 2 when it has anyone (+0x10e party count, +0x10f the rest). Ours showed set 3 as a second list of every
  alliance member.
- mapv3's row icon for set 2 is the party one for rows under the party count and the alliance one from there on.
- Members get flags 0x88: no label until the row is picked (FUN_101fa6d0 sets 8 on the set's ten, clears it on the
  pick, scrolls). The flag stays on the record, so the picked label survives a set change; ours forgot it.

**Where members come from.**

- At open (FUN_101f93c0), modes 0 and 5 only and only for a map of the zone we are in: every listed member after us
  whose actor has a model, when the sub-key under *them* equals the sub-key under *us*. Each goes through the s2c
  0x0A0 handler (FUN_101f94d0; in 30261006_0 FUN_101f7db0 calls FUN_101f7ec0 directly), so the pixel is the
  answer's: the record of (our zone, that key), or scale 0x10 when there is none. Event maps and the teleport preview
  get none. Ours filled them in every mode and compared with the shown record's key.
- The menu map opens on set 2 (30261006_0: FUN_101f7810 passes 2 for mode 0 to FUN_101f9a50), then FUN_101fc380(0)
  moves on past empty sets: with members placed, Markers opens on set 2 and asks for positions at once (map0's
  Enter, FUN_101f9270, asks when the set is above 1). Ours started on set 0.
- c2s 0x0D2 (FUN_101fa680, once per map, +0xa45): when Markers opens on set 2 or 3, and on every Left / Right in
  mapv3 whatever the set. A mode 5 map of another zone never asks (FUN_101fa620(0) presets +0xa45). Ours asked only
  when the set was 2 or 3 around the step.
- s2c 0x0A0 (FUN_100f07b0 → FUN_101f94d0): the packet's zone must be our zone, the member not us and listed, and
  the sub-key under the packet's position must equal the sub-key the map was asked for. Ours compared with the
  record's key and with the map's zone.

**Event maps are locked.** FUN_101f8ef0 opens every event map with the lock argument 1 (+0x10a) and set 1 for modes
1 and 4 (set 2 for the others, which have no mapv3). With +0x10a set, mapv3's handler returns at once and its open
leaves the window's input bit alone: no cursor, no keys. Ours let the arrows and Enter work there and only blocked
Escape. Set 0 needs +0xa46, which only modes 0, 5 and 6 work out, so an event map never has it.

**mapv3's names (FUN_101cb320 with 0x44), was inferred.** 0x44 is not a font: it is the width limit of the fitted
fontshp draw (the pen starts 8 in reserve, each glyph adds its width - 1, and at 68 the ellipsis sprite takes over).
Ours drew the whole name.

**The file edits without a window (ops 0x8b / 0xb8 / 0xa8 / 0xb9 with no event map open).** menu_mapframe_fn(4, zone,
key) → FUN_101f8ef0 with its last argument 0: a negative key is the sub-key under the loaded area's origin (0, 0, 0),
not under the player, and the file is named by it. Ours took the key under the player in the zone we are in.

**The sub-key for -1, everywhere (30261006_0: FUN_100b2570, FUN_101f78e0, FUN_101f79e0, FUN_101f7810).** None of
them tests the zone: FUN_101811d0 runs on the loaded collision whatever zone the map is of.

- Ops 0x89 / 0x8d / 0xc8 (FUN_100b9300 / FUN_100b9330 / FUN_100b9370) call FUN_100b2570(1, zone, key, flag, 0): the
  last 0 makes FUN_101f78e0 use the origin, as the file edits do. Ours used the player in our zone and 0 elsewhere
  *(inf)*, so an event map and a file edit of the same zone could name different files.
- The op 0xd4 preview passes 1 (under the player); its reopen and Change Map's mode 5 go through FUN_101f79e0, under
  the player too; the menu map (FUN_101f7810) under the player.

**FUN_100b2570's same-map test.** It keeps the op's mode (DAT_104882b4), zone (DAT_104896e6) and raw key
(DAT_104897f6) and reopens only when the mode or the zone differ, or the new key is not negative and differs from the
kept one. So a key whose sub-map has no record (the key-0 record shown) is still the same map, and further 0x8b
marks land on it. Ours compared with the shown record's key and reopened, dropping the unsaved marks.

**Ops 0xa8 / 0xb9 by sub (FUN_100b9780 / FUN_100b9820).** Sub 1 clears the slot in whatever map the window holds,
with no zone or key test. Sub 0 always goes through the file: FUN_100b2570(4, ...) closes an event map first, loads
the file, and FUN_100b2a60 → FUN_101fa420(1) saves it and closes whatever map was up. Ours cleared the open map's
slot when the zone matched (either sub) and edited the file only otherwise. Ops 0x8b / 0xb8 with no event map open
take the same file path, so they close a map that is up too.

**What that close does to the open map's marks (30261006_0).** They are dropped, not saved:

- The only call of the save, FUN_101f82b0, is in FUN_101fa420 (0x101fa420), and only with +0xa44 set and +0xfc not
  -1.
- An event map's mapframe close (FUN_1015e910 → FUN_1015e790 → FUN_10118f30 → the menu's handler at +0xc, the map
  object, whose +8 is the menu (FUN_10118f40): its vtable 0x1033a8b8 + 8, FUN_101fa550) closes map0 / mapv3 / mapv2 / scanlist / mapscan and frees +0x6c4 / +0x6c8 at once, without a save
  and without storing config 0x8a.
- The mode-4 open (FUN_101f9a50) then clears +0xa44 and loads the file over the records. The change sets +0xa44 again,
  and FUN_100b2a60 → FUN_101fa420(1) saves the file. It closes a map that is still up (the menu map: +0x6c4 still
  set) with the fade (vtable + 0x50, FUN_101ee580) and stores 0x8a.
- When FUN_101f9a50 refuses (on a lift, FUN_10129d90(0x1f) = group 7 0x61; no record for the zone, FUN_101f86b0 →
  0x20 = group 7 0x62), nothing is loaded. The change lands in the open map's records instead (FUN_101f8d50 through
  its +0xfc, FUN_101f8da0, FUN_101f8e30), and FUN_101fa420(1) saves them under that map's name, unsaved marks
  included.
  With no map open, +0xfc is -1 and nothing is saved.

Ours saved the open map's marks on that close. Now `through_file` and `MapWin::close_for_file` do the above.
