## Ship actors: the six open points, a new task's first frame, the far plane (2026-11-10)

<!-- dll-build: 30261102_0 -->

Modlog-gaps item 137 ("Ship actors: whether a new task first updates in its frame; vt +0x178 and the default speed
1.0 assumed; the far plane; the lighting area; the 10-second no-skip window; +0x130 bit 21's writer"). Addresses
are 30261102_0; the functions named in MODLOG "Ship actors" kept theirs, apart from the furniture draw
(FUN_101844c0 -> FUN_10185a90).

- A new task's first frame. The task list (manager DAT_1047e2f0) walks with a next pointer at +0xd5c
  (FUN_10074c30). The base constructor FUN_10074790 links a new task straight after the running one and sets that
  pointer to it (FUN_100750b0, 0x100750ff), so the walk runs it next, in the frame it was made. The path drive's
  update FUN_1005e9c0 (vtable 0x1032c9a4 +0x20) takes the frame's ticks off first, so a drive is one frame into its
  time on the frame it starts. Ours placed it without running its time (`fresh`); that is gone.
- A new scheduler's first step. FUN_10056c70 / FUN_10056b20 end in FUN_100748c0, which calls the task's whole
  update (vtable 0x1032c860 +0x20 = FUN_10057e10) with itself as the running task. That update takes the frame's
  ticks off the countdown before the first op, and the carry comes off the first wait that is not 0. So every wait
  after a start is one frame shorter than the file says, and the same holds for a sub-scheduler an op starts. Ours
  ran the first step with no ticks. `Effects::run_new` and the end of `fast_forward` now take the frame's ticks
  (`frame_dt`). Hume fist sparks start at tick 42 instead of 45 at 1-tick frames (three starts on the way).
- With both, a ship's sequence and its first drive count the same clock from the frame they start. A drive the next
  op 0x26 / 0x27 replaces still dies 2 ticks before its end, as before.
- The op's order (0x1005ca07..0x1005ca78): the actor's path drives are deleted first, then the Vtx must resolve
  (FUN_1004e3b0), then the actor's vt +0x178. Ours checked the path first; an op whose path is missing now still ends
  the running drive. The drive's time is `__ftol(duration x speed)` (0x1005cad3): whole ticks. The constructor's
  eleventh argument (flags & 0xf0) is not stored; +0xac is always 1.
- vt +0x178 (FUN_10081fb0) sets actor +0x88 bit 0 and answers whether it was clear; vt +0x17c (FUN_10081fd0) clears
  it from the drive's destructor (FUN_1005f2c0). The op is the only caller of +0x178 and the destructor the only
  caller of +0x17c, and the op has just deleted every path drive on the actor, so the test always passes. The bit is
  "a path drive holds this actor" (ours: `Effects::driving`). A rotation drive (0xa9 / 0xaa) does not take it.
- The default speed. FUN_10057270 -> FUN_100573e0(resource, n, ...): n 0 gives +0x9c = 1.0, n 1 gives 1.0 and sets
  +0x141, any other n gives n / header +0x7c. A ship's start passes 0 on both paths (FUN_10056c70(actor, actor, 0,
  0), FUN_10056b20 -> FUN_10056ce0(actor, actor, 0, 0)). A sub-scheduler copies its parent's +0x9c. So 1.0 stands.
- The 10-second window (FUN_10097a80 / FUN_100c4730, 0x100c47ab..0x100c47cf). now = FUN_10103b30() x 60 and start
  = +0x184 x 60, both 32-bit products that wrap; a start product of 0 is taken as now; elapsed = now - start, compared
  signed (`jl` at 0x100c47ba). Below 600, which includes a start still to come, the sequence plays from its first op;
  from 600 up it is caught up. Ours used 64-bit numbers: `ships::skip_ticks` now does the same arithmetic (a start
  more than 2^31 ticks old wraps negative and plays from the first op).
- The far plane. The model actor's draw depth +0x8c is set to 1.0 when its file is set (FUN_100c4290 -> FUN_10085000)
  and nothing else writes it, so the actor draw loop (FUN_10082d70: no draw below 0 or with +0xb2 set) always draws
  it: no distance test. The projection's far plane is 65535 (camera +0x2e0, FUN_100153d0; the only other writer,
  FUN_10015430, has no caller). Ours' far plane was 2000. Selbina's ferry (file 31008) sails to x = 1983, about
  1,975 units from its berth, so ours cut it at the far end where retail still draws it. `render::FAR` is now 65535.
  Before and after zone shots (248, 230, 126, 102) differ only by rounding in the sky (1 level) and a few single
  pixels on edges. Test `path_reach_census` prints each ship file's path bounds.
- The lighting area. FUN_10185a90 reads the light, ambient and fog through FUN_1018cf70 / FUN_1018cfb0 /
  FUN_1018cff0 with ECX = DAT_1065dcbc and an area argument of 0, which skips the area lookup (FUN_10189f90).
  DAT_1065dcbc is the first environment record, made once (FUN_1018c700). The light is set 0 of FUN_1018a270
  (the scenery's, +0x14c / +0x16c). So "area 0, lit as the scenery" was right.
- +0x130 bit 21. The only writer is the CXiSklFurnitureActor constructor (FUN_100ab360: +0x130 |= 0x200008, already
  in MODLOG "Mog House"). The setter FUN_10083360 has no call, jump or pointer anywhere in the DLL. Readers:
  FUN_10083340 (the model switch's furniture table, FUN_100d2f60 case 2) and FUN_10098210 (not a target). Ours
  builds these actors already (skinned furniture), so nothing is left of "Not done: +0x130 bit 21".
- A prop's 'init' (FUN_100c47f0, re-read): the first update after the file is set only snaps the heading (+0x779
  clear). From the second, the generic MMB branch goes through 'init' once: played when +0xb2 is 0, passed over for
  good when the model is hidden then (+0x77a is set either way). FUN_100c4290 clears both flags, so a model swap (op
  0xb6 0x11) goes through it again. Ours played 'init' at creation whatever the hide; `ships::apply` now follows
  retail (`ModelActor.updated`, `.init`).
