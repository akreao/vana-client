## Effect tasks: the weather ops change the weather inside the op (2026-11-27)

<!-- dll-build: 30261102_0 -->

Modlog-gaps item 188 (split from 181): scheduler ops 0x7b / 0x7c / 0x7e / 0xae work on the zone object's weather
objects inside the op, so their generators and schedulers start and end there, in the task walk. Ours queued them
(`Effects::env_ops`) and the client applied them after the walk. The scheduler's jump table is 0x1005dc1c (index
op - 2): 0x7b -> 0x10057fdf, 0x7c -> 0x1005801e, 0x7d -> 0x10058005, 0x7e -> 0x10058469, 0xae -> 0x1005d01f.

- The weather change, FUN_10188ac0(this = the zone object DAT_1065dcbc, tag, a time, the blend time), `ret 0xc`:
  - no file (+0x14): a message and nothing more (0x10188ac6);
  - the linked object (+4) first, with the same three arguments (0x10188af8);
  - blend time 0 and the newest weather object's tag (FUN_10189680: +0x10 of the object at +0x10, 0 with none) not
    `tag`: every weather object is deleted, the ones behind the newest first (0x10188b10..0x10188b52: FUN_1018c1c0,
    then the free), and +0x10 is cleared;
  - the newest object's tag still not `tag`: 0x46 bytes and FUN_1018bd70(the zone object, tag, the blend time).
  The second argument is only handed to the linked object's call: nothing reads it.
- A weather object's constructor, FUN_1018bd70:
  - its folder (+0xc): the file's first `weat` folder (FUN_100724c0 from +0x14: file order, the start folder
    included), then the first folder named `tag` inside it, else the first named `suny` (0x1018be19); with no `weat`
    the whole file is searched. Neither found: messages, and the object is returned without being linked
    (0x1018bf6d..0x1018bfd6), so no weather is in force;
  - every task of every scheduler under `weat` is deleted (0x1018be53: FUN_100742b0 kind 7, FUN_10056eb0 ->
    FUN_10074ab0);
  - every self-starting scheduler under the folder (FUN_10056e80: an end loop or an op 0x52, and no op 0xa2) starts
    on no actors with its first update at once (0x1018beea: FUN_10056b80 -> FUN_10056ce0, FUN_100748c0);
  - +0x18 = the blend time, +0x14 = the same; the object is linked as the newest (+8 = the old newest, 0x1018bf26);
    +0x10 = the tag of the folder found, so `suny` after the fall back;
  - every generator under the folder with flag 0x1000 starts (FUN_10072540 kind 5 with FUN_1018c020 ->
    FUN_100531d0, its +0x64 = the object): its task is moved before the running task (FUN_10074a00) or to the front
    of bucket 9 (FUN_100749b0(9), the attached modes). Under a roof (the zone object's +0x1bc) one is passed by when
    its op 1 has flag 0x4000000, or flag 4 unless FUN_100539e0 holds (generator flag 0x400, or op 1's life 0).
- Its destructor, FUN_1018c1c0: the generators whose +0x64 is the object stop and lose their elements
  (FUN_1018c180: FUN_100538e0(0), FUN_10053890(0)), in the global file (DAT_1047e2d8) and in its folder; the zone
  object's env pointer goes back to the static block when it was the object's (FUN_10189690(0)); the object leaves
  the list; every task of every scheduler under its folder is deleted (0x1018c2da).
- Op 0x7c (0x1005801e), with a zone object: FUN_10188ac0(4cc @8, the op's duration i16 @6, 0). The duration is the
  argument nothing reads, and the blend time is 0: the older weather objects always go at once. Ours blended the env
  over the duration.
- Op 0x7e (0x10058469): the scoped 0x2f block 4cc @8 (FUN_10072290; none: nothing) + 0x30 to FUN_1018c5e0: 0x2b
  dwords over the static env DAT_1065dc10 (FUN_1018bd30), the fog and light globals from it, then FUN_10189fe0
  deletes every weather object of every zone object and each one's env pointer is put on the static block
  (FUN_10189690, 0x1018c65e). So the weather's generators and schedulers end, no tag is in force (the next
  FUN_10188ac0 makes an object even for the tag there was), and the scene is lit by the block: FUN_10188a70, each
  frame, takes a weather object's env (+0x20, the static block when it has none) only while there is an object.
  Ours kept the weather's effects and lit the scene by the block only where the zone had no env for the weather.
  The static block is written by the zone object's constructor (FUN_1018c740: the default) and by this op only.
- Op 0xae (0x1005d01f): the weather tag table. The zone object's +0x1d8 points at one of two tables of twenty 4ccs,
  0x10378c80 (`fine` `suny` `clod` `mist` `dryw` `heat` `rain` `squl` `dust` `sand` `wind` `stom` `snow` `bliz`

  op: i = the newest weather object's tag in the table in force (FUN_1018d0f0: 0 when it is not there); the table
  becomes u32 @8 (FUN_1018d0b0: above 1 is 0); FUN_10188ac0(the new table's entry i, 0, trunc(f32 @0xc x 3600)).
  So the weather in force goes to its folder of the other table, blended in over f32 @0xc Vana'diel minutes (3600
  clock units each, 1500 a second) beside the old object, or at once with 0. The server's weather numbers go
  through the same table from then on (FUN_1018d0e0 in FUN_10094190, FUN_1009f2f0, FUN_10094040, FUN_100940b0).
  The scene load FUN_1018c970 puts table 0 back (FUN_1018d0b0(0)). Ours had no table and no op 0xae.
- Op 0x7b (0x10057fdf), with a zone object: FUN_1018c970(u32 @8), the scene load of a zone-in (table 0, then
  FUN_1018cad0 -> FUN_1018cbf0 deletes the weather objects and loads the scene's file).

Built:

- `Effects::change_weather` is FUN_10188ac0 with FUN_1018bd70's steps in retail's order (the schedulers before the
  generators; ours started the generators first), `end_weathers` / `end_weather` FUN_10189fe0 / FUN_1018c1c0. Ops
  0x7c, 0x7e and 0xae call them inside the op: a new scheduler takes its first update there (`run_new`), so a task
  it makes sends the walk back to the op's scheduler, and each generator's task is a moved node.
- The object's tag is its folder's name, the folder is looked up as FUN_100724c0 does, and the roof rule is
  FUN_1018c020's (flag 4 no longer stops a static generator).
- `Effects::weather_table` with `weather_tag(number)`; the client names the server's numbers through it (zone-in,
  s2c 0x057, event ops 0x77 / 0x78 / 0xae sub 0, the event's end, the scene loads).
- A zone-in into the scene ours still has loaded does the scene load's part (`Effects::reset_weather`: table 0, the
  weather objects deleted) and makes the zone-in's weather.
- Leaving a roof (FUN_1018cbb0 -> FUN_10188bb0 -> FUN_1018c0b0) starts every weather object's camera emitters
  that are not running, so also the ones a weather made under the roof passed by; ours only resumed the stopped ones.
- The client's side (`EnvOp`): the env's weather objects are kept by tag (`World::weather_chain`); op 0x7e clears
  them (`weather_off`: the static env alone, for the areas too) and the static env is no longer dropped by op 0x7c.
- The title's movies (client/flyover.rs): op 0x7e ends the weather's effects and lights the scene by its block
  until the next op 0x7c; after that the block is only what a weather without an env falls back to.

Not built (queue rows 215..218):

- The starts outside the walk (zone-in, s2c 0x057, the event ops) still take their first update at the next walk
  (row 212).
- A zone object's linked objects (the areas, FUN_10188970) get their own weather objects through FUN_10188ac0's
  first step, with the generators and schedulers of the area's folders; ours keeps the areas' env keys only.
- The static env's life: ours drops it at a zone change. Retail writes DAT_1065dc10 only in FUN_1018c740 and op
  0x7e; when the zone object is deleted (its vtable +4, FUN_1018c930, on messages 2 and 5) and made again is not
  traced.
- The title's movies between op 0x7b and their first op 0x7c: retail has no weather object there; ours starts
  `suny` with the scene. And the movies are not schedulers of the task list.
- `ZoneWeather::at` falls back to the file's first weather folder when neither the tag nor `suny` is there; in this
  build FUN_1018bd70 leaves the object out of the list in that case (the static env).
- Under op 0x77's hold a scheduler's weather is kept as a number of the table in force; a tag outside it is not.
