## The game's line breaker and its language rules (2026-11-24)

- FUN_1025ccf0(out, cap, src, &used, max, extra, tail, fit, width) cuts one line. `fit` (FUN_1011ee00 =
  FUN_1011e810(s, 0, max)) is the bytes whose summed char widths (FUN_1011e350: below 0x20 none, 04 skipped, a short)
  stay within `max`; `width` is FUN_1011e400(s, n). A text that fits ends at its first line break (07, CR, LF;
  FUN_1025d450), and one ending in a soft hyphen (0x15) gets '-' (DAT_10354e04). Else a line break inside the width
  ends the line. Else, by the client language (DAT_10457bd8 +8; German and French with +0x18 bit 7 as English):
  - Japanese: chars; when the char where the width ends is 、。！ (FUN_1025d130, table 0x1038bd94, needs 2 bytes
    left), the line ends before the last char, which goes down with it.
  - English, German, French: whole words (FUN_1025d210) while their bytes stay under `cap`; then soft hyphens inside
    the next word (FUN_1025d410) while the line with '-' still fits. A word may end after a space, or after an entry
    of 0x1038bda4 (85 45, "...", 81 9A, '-') unless one of it or 0x1038bdcc (' ', '?') follows; a space before a dash
    (FUN_1025d190: '-' not before 0..8) does not end one. French (language 3) keeps a space before 82 49, 85 7B,
    ! ? : ; and the space after 85 6B / 85 4B (its opening guillemets).
  - If fewer than `tail` bytes of the word that does not fit lie inside the width, the line ends at the last word (or
    at a soft hyphen there with '-'; `extra` is weighed in, every caller passes 0); else it is cut where the width
    ends. The space a line ends at stays on it; soft hyphens are never copied (FUN_1025cc10).
  - Unreachable in retail: when the width ends on a line break (it has no width) the line copies `extra` (0) bytes.
- Callers: FUN_1012b980 (old FUN_1012a4f0: the log's FUN_1012a170 / FUN_1012a520 with buffers 0x7ff / 0x1ff, the
  event pages FUN_101280f0, the message queue FUN_10137a70 / FUN_101383d0 with 0x200) tail 0x18; the text boxes
  FUN_10158200 / FUN_101582a0 (window print FUN_101186d0, the comyn question FUN_10212660) tail 0x14, buffer 0x200;
  the item description FUN_1015c9e0 (old FUN_1015b410) tail 0x14, buffer 0xff, 316 px; Japanese (language 0) has
  FUN_1011ee70 as `fit` (a 、。！ where the width ends hangs on the line with the widthless chars after it) and lines
  2.. 366 px. The description lines are the source bytes the breaker took, cut at a newline (FUN_10316810), at most
  20; no '-' is drawn there. FUN_1015c9e0 does the same for a second text at +0xc (20 more lines), not traced.
- Ours: dat::linebreak is the breaker on Shift-JIS bytes (line_for / lines_for take the language, line / lines the
  client's), str_lines runs it over a decoded String (a char that is no single game char stands as a pair FC xx of
  its own width; widths in 1/16 px). GameUi::wrap_indent / wrap_spans (log, event pages) use tail 0x18, GameUi::wrap
  (text boxes and the other windows that wrapped with it) 0x14; they replaced a greedy space wrap that trimmed the
  line ends. iteminfo's description follows FUN_1015c9e0 (it wrapped each line at spaces at 316 px). Ours takes a char
  wider than the whole line alone where retail's loops would never end.
- Tests: dat::linebreak::tests (words and the tail, line breaks, dashes and ellipses, French spaces and the European
  flag, soft hyphens, Japanese with and without the hang, decoded text).
