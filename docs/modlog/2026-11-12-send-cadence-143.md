## Send cadence: the interval that follows the server, and what else the send path does (2026-11-12)

<!-- dll-build: 30261102_0 -->

Queue row 143. The row named two things. The per-id 1000 ms refusal was already built ("Net: the per-id 1000 ms
send gate", 2026-11-03), so that half was an audit. The interval step was not built, and reading its function
turned up more that ours did differently. All addresses are build 30261102_0.

**The send timer (FUN_100fa2d0 / FUN_100fa5f0).** Each frame, `FUN_100dbfe0(0, net +0x417c)`: timer 0 adds the
frame's ms and fires once it reaches the interval at +0x417c, then starts again from 0. A fire runs FUN_100fab40,
which builds and sends one datagram. The same timer carries the login datagrams (connection states 1 and 2) and
the game's (state 3).

**Where the interval comes from.**
- The base is PacketCnt, DAT_104e0f44 +0x44c5c. session_start (FUN_100f9a80) stores its argument there: the
  config's +0xd0, 400 (FUN_10103480), passed down through FUN_100f0270 and FUN_100f9b70.
- At the connect FUN_100fa000 sets the interval to **5 × the base** (0x100fa044 `lea eax, [eax + eax*4]`): 2000 ms.
  Nothing resets it at the zone-in (the only writers of +0x417c are the connect, the step below and s2c 0x005).
- s2c 0x005 (FUN_100fadf0, registered by FUN_100f9c60): u32 at 4 becomes the base and the interval at once.

**The step (FUN_100fab40, 0x100fab53..0x100fabcf).** Only in state 3, before each datagram is built:
```
d = (u16 net+6, the sequence this datagram will carry) - (u16 net+0xA, the server's ack of ours: its header @2)
if d < -1 or d > 1:    interval += 50; at most base + 3000
else if interval > base: interval -= base; at least base
```
Both are zero-extended and subtracted as ints, with no wrap handling. In step means the server has acknowledged the
datagram before this one. So:
- After every connect the interval starts at 2000 and comes down by 400 per datagram: the login is repeated every
  2000 ms, and after the zone-in the game's datagrams go 2000, 1600, 1200 and 800 ms apart before settling at 400.
- Each datagram sent while the last one is still unacknowledged adds 50 ms, up to 3400. Once the server has caught
  up it comes down by 400 a datagram (3400 takes eight).

**The sequence (0x100fad1c).** +6 is incremented after a datagram is sent, and 0 is stepped over (0xFFFF is
followed by 1): sync 0 marks a queue slot that has not gone out yet.

**The queue (FUN_100dda10 / FUN_100dda60).** 30 slots of 0x110 bytes, 10 of them kept back. A slot is given while
free ≥ 10 (0x100ddaff `cmp [kept], free; jle`), so the 21st waiting packet still gets one and the 22nd is refused;
the ids registered with FUN_100dddc0 (0x00C and 0x0F2, FUN_100fa000) may use the kept ones, up to 29 waiting. A
slot stays taken until the server's ack reaches the sequence it first went out with (FUN_100fdd40). FUN_100fc510
has already stored the id's gate time when the queue refuses (0x100fc5d9 comes before the call at 0x100fc5f0).

**The gate (FUN_100fc510).** As in the 2026-11-03 entry, with one correction: the test at 0x100fc56a is `now <=
last + 1000` (jbe), so the gate opens at 1001 ms, not 1000. The interval table (+0x43ee4, 0x120 ids) is filled
with 1000 by session_start and written nowhere else.

**The datagram (FUN_100fdd40 / FUN_100dd590).** Slots are copied in order while header + sub-packets stay within
3999 bytes. The second limit, an estimated compressed size against DAT_104e1ca4 +0x448 - 0x31, never applies:
nothing in the DLL writes +0x448 (searched by displacement), so the unsigned limit is 0xFFFFFFCF *(inferred from
the zeroed config block)*. The compressed datagram must fit 0x550 bytes or FUN_100dd590 returns -1 and nothing is
sent that tick (the sequence does not advance).

**Not used.** +0x4194..+0x41a4 measure time spent sending with no answer (5 or more datagrams since the last
read), and +0x4194 set would zero movement axes 4 and 5 (FUN_10124e00). Its thresholds +0x4198 / +0x419a are only
ever zeroed (the zone-in handler FUN_100fae40) and printed (FUN_100fc000), so the flag can't be set.

What changed in ours (client/net.rs, net/map/session.rs):
- The interval is a session value: 5 × the base at the connect, stepped by `step_interval` before each datagram
  once zoned in, from `MapSession::lag`. The login repeats on the same timer (2000 ms; it was 400). The base
  follows one rule (`wanted_interval`): a mod's `send_interval`, else Settings' Send Rate when faster than 400 on a
  private server, else the server's s2c 0x005, else retail's 400. A change of any of them sets base and interval
  at once. Retail's connect interval is always 2000: session_start zeroes the block holding PacketCnt before it
  stores the config's 400 (FUN_100f9940 / FUN_100f9a30 in 30261006_0; run before every connect *(inferred: the zone
  change's address goes into the block the connect reads, DAT_104df770)*). Ours caps 5 × the base there, so a mod
  at 1000 ms does not slow the login and the first sends after the zone-in to 5 s.
- s2c 0x005 is handled, under the rule above; its value lasts the session, as PacketCnt does.
- The sequence steps over 0 (ours sent sequence 0 after 65535 datagrams, about 7 hours).
- A sub-packet gets its sync when a datagram first carries it. Ours stamped it when queued, so one left out of a
  full datagram could be taken as acknowledged without ever being sent.
- The queue's room rule: with 21 waiting a send is refused (dropped, or held for the ids ours retries); 0x00C and
  0x0F2 up to 29. A refused gated id has used its second, held ones too, so a retry goes no sooner than a second
  later. Chat, tells and fishing (0x0B5, 0x0B6, 0x110) ask for room where they are made, in `call_gate`, from the
  slot count the network thread publishes (NetStats::waiting), so their callers see the refusal as retail's do.
- The gate opens at 1001 ms.
- The raw limit is 3999 - 28 (was 4000), and a datagram never exceeds 0x550 bytes. Difference kept on purpose:
  where retail sends nothing until the same datagram fits, ours sends the oldest sub-packets that fit and leaves
  the newest for the next datagram. The session's last datagram (0x00D, answering s2c 0x00B) always carries
  the 0x00D and leaves older ones out instead, since no datagram follows it. A sub-packet that alone compresses
  past 0x550 bytes, which no retail datagram ever carries either, is dropped rather than holding up the rest. The
  sizes come from the code lengths (`Codec::bits`), so each datagram is compressed once.
- `FFXI_NET_DROP=n` throws away n % of the datagrams read, as retail's DAT_104e1ca0 +0x184 does (0x100fa7f1). It
  is there to test the step.

Packets the mods send (`SendBatch`) go out at once as before, outside the queue rules.

Found and not built (left):
- **Replace-mode sends.** FUN_100fc510's second argument, when not 0, skips the gate and makes FUN_100dda60 look
  for a waiting slot of the same id whose stored key (the third argument of the call that made it) equals it; that
  slot is rewritten and goes out again with a new sync, so only the newest of such a packet is sent. Call sites
  with (force, key): (1, 1) for 0x00A 0x00B 0x00D 0x03C 0x076 0x078 0x0BE..0x0C2 0x0C5 0x0C6 0x0C9..0x0CB 0x0DB
  0x0DC 0x0F2 0x101, 0x0D1 and 0x0D3 by kind, 0x033 kinds 1..3; (1, 0) for 0x04B 0x04D 0x04E, (n, 0) for 0x01A
  and 0x116, (2, 3) for 0x01E and (1, 2) for 0x01F, which never match; a register for 0x015 0x016 0x035 0x03B 0x042 0x050 0x05E 0x082..0x084 0x0E1 0x0E8
  0x0FA..0x0FF (not traced). Ours rewrites only the position (0x015).
- **The connection timeout.** In state 3, FUN_100fa2d0 ends the session (state 4, message 0xFA1) when no datagram
  has been read for +0x41b0 = 3 × config +0xc = 90 s by default.
